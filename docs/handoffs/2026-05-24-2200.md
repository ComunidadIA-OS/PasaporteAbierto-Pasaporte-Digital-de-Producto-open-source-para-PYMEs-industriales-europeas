## Decisiones tomadas

- **Adopción de flujo `task-branch → develop → main`** (decisión del usuario en sesión 2026-05-24, persistida como `feedback-git-workflow-develop.md`). Toda PR futura va contra `develop`; `main` solo recibe `develop` cuando hay versión testeada. Las ramas de tarea se crean siempre desde `develop` actualizado, no desde `main`.

- **Reserva del término "fase" exclusivamente para F1–F6 del hackathon** (decisión del usuario, persistida como `feedback-nomenclatura-fases.md`). No usar "Fase 1/2/3/4" como agrupación táctica intra-sesión — causó confusión real en esta sesión. Tickets son `Fx-yy`, tareas son `T<N>`. Para sub-chunks intermedios usar prosa descriptiva.

- **F1-03 cerrado con cobertura validada contra texto oficial del Reglamento UE 2023/1542** (no contra Battery Pass v1.3 alone). Tras descargar el PDF (DOUE L 191/28.7.2023, 117 páginas) se confirmaron las 5 citas erróneas del plan original y se reescribieron alineadas con Anexo XIII. Análisis auditable persistido en `docs/research/battery-pass-v1.3-mandatory-attrs.md`.

- **Sección 4 del Anexo XIII (datos individuales dinámicos: SoH operativo, ciclos consumidos, accidentes, temperatura, SoC) intencionalmente fuera del alcance** del plugin estático. Razón: son datos de telemetría operativa post-registro emitidos por el BMS, no por el fabricante al registrar el modelo. Documentado con comentario inline en `plugins/batteries.yaml` antes del bloque `required_documents:` y referenciado en ARCHITECTURE.md §"Identificador único y niveles de acceso del DPP".

- **`identifier_scheme: iso_iec_15459` para baterías; `gs1_digital_link` como fallback genérico para sectores sin acto delegado específico**. Razón: Art. 77.3 obliga literalmente a ISO/IEC 15459-1/2/3/4/5/6 para el identificador único de pasaportes de batería. Implementado con `Literal` en `Plugin.identifier_scheme` (commit `043cd76`); la columna `gs1_uri` de `published_dpps` se conserva como nombre histórico, agnóstica al contenido. ADR formal aplazado.

- **`access_level` por campo, ortogonal al `provenance`** (commit `043cd76`). Modela las 4 secciones del Anexo XIII (`public` / `legitimate_interest` / `authorities_only` / `individual`). Default `public` para backward-compat. El endpoint público sólo expone `public`; los demás niveles quedan habilitados por la columna del campo y por endpoints específicos planificados para fases posteriores.

- **`extra="forbid"` en los 5 modelos Pydantic del loader** (heredado de T5 con fix `c01ff8a`, preservado en T5.1). Un typo en una clave (`citaton`, `acess_level`, etc.) se rechaza inmediatamente en vez de fallar más tarde como "campo ausente". Crítico para contribuidores externos (F6-04).

- **Política `feedback-commit-after-validation` aplicada con éxito en T5, T5.1 y T6**: el implementer subagent NO commitea; el controller commitea al final tras spec compliance review + code quality review APPROVED. Los nits del code review se aplican antes del commit cuando merecen la pena (en T6 se aplicaron 3 Important + Minor pedagógicos para mantener "perfecto").
