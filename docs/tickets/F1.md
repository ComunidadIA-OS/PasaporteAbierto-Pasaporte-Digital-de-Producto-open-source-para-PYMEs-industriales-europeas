## F1-01 · Scaffolding del monorepo
**Etiquetas:** backend, frontend, infra

**Historia de usuario**
Como desarrollador del equipo, quiero un monorepo arrancable en menos de 30 minutos con backend, frontend y observabilidad para empezar a iterar el mismo día.

**Descripción**
Monorepo con backend FastAPI 0.115 / Python 3.11 / SQLModel / Pydantic v2 y frontend Next.js 16 con App Router, TypeScript estricto, Tailwind CSS y shadcn/ui. Docker Compose con cuatro servicios: backend, frontend, Langfuse self-hosted y Ollama opcional. Incluye `.env.example`, `Makefile` con atajos básicos y healthchecks por servicio.

**Criterios de aceptación**
1. `docker compose up` levanta backend, frontend y Langfuse sin errores; Ollama queda opt-in vía profile.
2. `GET /api/v1/health` responde 200 con versión, modelo activo y backend de LLM.
3. README inicial documenta el setup completo en ≤30 minutos.

## F1-02 · Modelo de datos SQLite (5 tablas de la arquitectura)
**Etiquetas:** backend

**Historia de usuario**
Como sistema, necesito las cinco tablas definidas en la arquitectura para persistir sesiones, documentos, campos extraídos, audit log y DPPs publicados.

**Descripción**
Migraciones con SQLModel para las tablas `sessions`, `documents`, `extracted_fields`, `audit_log` y `published_dpps` exactamente como define la arquitectura. Define FKs, índices, y deja preparado el campo `prev_hash` en `audit_log` para el hash chain. Incluye seed mínimo de una sesión demo y un script de reset.

**Criterios de aceptación**
1. Las cinco tablas existen con los campos descritos en la arquitectura, sin renombrados.
2. `audit_log` tiene índice sobre `id` y restricción que vincula `prev_hash` con la fila anterior.
3. Migración reversible (`upgrade` / `downgrade`) y seed reproducible con un solo comando.

## F1-03 · Esquema de plugins YAML + plugin baterías
**Etiquetas:** backend, ia

**Historia de usuario**
Como sistema extensible, necesito que cada sector ESPR se modele como un YAML en `plugins/` para que la comunidad pueda añadir actos delegados sin tocar el núcleo.

**Descripción**
Define `plugins/_schema.yaml` con la interfaz del plugin: campos del DPP (con su cita normativa, `access_level` y obligatoriedad), documentos requeridos, validaciones, y `identifier_scheme` declarado por el plugin. Implementa `plugins/batteries.yaml` cubriendo Reglamento UE 2023/1542 conforme al texto oficial del **Annex XIII**: las tres secciones estáticas (1 pública, 2 interés legítimo, 3 autoridades) son in-scope del wizard; la Sección 4 (datos dinámicos individuales) se reconoce en el schema pero queda fuera del alcance porque corresponde a telemetría operativa. Loader Python valida cada plugin contra el schema en arranque. Cada campo del plugin debe declarar su cita normativa (reglamento + artículo o anexo) y su `access_level`.

**Criterios de aceptación**
1. El loader rechaza con error claro cualquier plugin que no cumpla `_schema.yaml` (incluyendo `access_level` con valor fuera del enum y `identifier_scheme` desconocido).
2. `batteries.yaml` define **≥25 campos obligatorios** que cubren las tres secciones estáticas del Annex XIII del Reglamento UE 2023/1542 (Sección 1: ≥19 ítems públicos; Sección 2: ≥4 ítems de interés legítimo; Sección 3: ≥1 ítem de autoridades), cada uno con su cita normativa exacta al artículo o letra del anexo, y `access_level` correcto.
3. Tests unitarios cubren al menos un plugin válido y tres inválidos (campo faltante, cita ausente, `access_level` fuera del enum).
4. `identifier_scheme` del plugin de baterías es `iso_iec_15459` (Art. 77.3 del Reglamento UE 2023/1542); el plugin loader acepta también `gs1_digital_link` como esquema por defecto para sectores sin acto delegado específico.

## F1-04 · Router de modelos con LiteLLM
**Etiquetas:** backend, ia

**Historia de usuario**
Como fabricante PYME, quiero poder elegir entre un modelo local gratuito y una API comercial cambiando una sola variable de entorno, sin tocar el código.

**Descripción**
Capa fina sobre LiteLLM con un wrapper `llm.complete(prompt, **opts)` único para todo el sistema. La variable `MODEL_BACKEND` selecciona el backend: `ollama:qwen2.5:14b`, `ollama:llama3.1:8b`, `anthropic:claude-...`, `openai:gpt-...`. Por defecto, modo local con Qwen 2.5 14B para que la PYME no necesite cuenta cloud.

**Criterios de aceptación**
1. Cambiar `MODEL_BACKEND` no requiere recompilar ni tocar otros módulos del backend.
2. Las trazas en Langfuse incluyen el `model` y el `backend` realmente usados.
3. Un test verifica que si el backend no responde, se devuelve un error tipado y trazado, sin pantallazo.

## F1-05 · Observabilidad con Langfuse self-hosted
**Etiquetas:** infra, ia

**Historia de usuario**
Como equipo, quiero ver en tiempo real qué decide cada componente IA para depurar y demostrar el sistema sin abrir logs crudos.

**Descripción**
Langfuse self-hosted en docker compose. Decoradores `@trace_classifier`, `@trace_collector`, `@trace_chat` que registran prompt, modelo, tokens, latencia y output. Cada componente IA aparece como un span diferenciado. El audit log y las trazas Langfuse son canales independientes (no se mezclan).

**Criterios de aceptación**
1. UI de Langfuse accesible en `localhost:3001` tras `docker compose up`.
2. Una corrida del wizard demo produce trazas separadas para Clasificador, Recolector y Chat.
3. La traza incluye `cita_normativa` cuando aplica (Clasificador, Chat).
