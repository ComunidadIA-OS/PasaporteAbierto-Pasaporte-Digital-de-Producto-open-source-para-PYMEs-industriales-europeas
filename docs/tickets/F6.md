## F6-01 · Manejo de errores y estados de carga end-to-end
**Etiquetas:** frontend, backend

**Historia de usuario**
Como fabricante, quiero ver siempre algo claro en pantalla, también cuando el sistema tarde o falle, para no quedarme con dudas sobre lo que está pasando.

**Descripción**
Error boundaries en React. Toasts coherentes para éxito / aviso / error. Estados `loading`, `error`, `success` explícitos en cada llamada IA. Retry automático x3 con backoff exponencial para timeouts del LLM. Mensajes de error humanos (no stack traces) en la UI.

**Criterios de aceptación**
1. Ninguna pantalla queda en blanco ante un error de API.
2. Un timeout del LLM muestra mensaje y botón "Reintentar".
3. Todos los formularios reflejan estado `cargando / éxito / error` durante el envío.

## F6-02 · Tests E2E del flujo completo (Playwright)
**Etiquetas:** test, backend, frontend

**Historia de usuario**
Como equipo, quiero confianza en que el pipeline completo funciona de extremo a extremo y no se rompe entre demos.

**Descripción**
Playwright recorre el wizard completo con datos dorados de cada sector. Test del Recolector con un PDF dorado verificando ≥80 % de extracción. Test del Chat con 10 preguntas de referencia comprobando que el 100 % devuelve cita normativa. Los tests pueden correr offline contra un LLM local (Ollama) para que la CI no dependa de claves externas.

**Criterios de aceptación**
1. `npm run test:e2e` pasa en local y en CI (GitHub Actions).
2. Los tests de Recolector y Chat funcionan con LLM local sin necesidad de APIs comerciales.
3. La salida del E2E genera un informe HTML adjuntable a la PR.

## F6-03 · README + diagrama de arquitectura + quickstart Docker
**Etiquetas:** docs

**Historia de usuario**
Como contribuidor nuevo, quiero entender la arquitectura y levantar el proyecto en menos de 30 minutos siguiendo solo el README.

**Criterios de aceptación**
1. Un dev sin contexto previo levanta el sistema y genera un DPP demo en ≤30 minutos.
2. El diagrama coincide con la arquitectura real al cierre del hackathon.
3. README contiene enlaces directos a guía de plugins, DPGA y licencia.

## F6-04 · Plugin textil de ejemplo + guía de contribución de plugins
**Etiquetas:** backend, docs, ia

**Historia de usuario**
Como desarrollador externo de la comunidad, quiero contribuir un plugin para mi sector siguiendo una guía clara, sin tocar el núcleo del sistema.

**Descripción**
`plugins/textile.yaml` siguiendo el `_schema.yaml` (F1-03), cubriendo los campos ESPR aplicables a textiles. Documento `docs/plugins.md` que explica la interfaz completa en ≤500 palabras con un ejemplo paso a paso. Test de contrato (`tests/plugins/test_contract.py`) que cualquier plugin nuevo debe pasar para ser aceptado.

**Criterios de aceptación**
1. El plugin textil funciona en el wizard sin tocar código del núcleo.
2. `docs/plugins.md` explica la interfaz completa en ≤500 palabras.
3. El test de contrato detecta automáticamente plugins inválidos o mal documentados.

## F6-05 · Documentación DPGA, sello Pasaporte Abierto y licencia
**Etiquetas:** docs, infra

**Historia de usuario**
Como proyecto, queremos ser reconocidos como Bien Público Digital y dejar claro a la comunidad cómo unirse al ecosistema Pasaporte Abierto.

**Descripción**
Licencia Apache 2.0 verificada en repo. Cuestionario DPGA cumplimentado en `docs/dpga.md`. Indicadores de impacto iniciales documentados (instalaciones, DPPs generados, sectores cubiertos por plugins de la comunidad). Sección "Pasaporte Abierto" en el README explicando el proyecto, su misión y el proceso para postularse como instancia oficial.

**Criterios de aceptación**
1. El repositorio es público con licencia OSI aprobada (Apache 2.0).
2. `docs/dpga.md` está cumplimentado y enlazado desde el README.
3. El README incluye sección "Pasaporte Abierto" con misión, métricas iniciales y proceso de adhesión.
